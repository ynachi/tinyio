Storage engine internals · v2 implementation guide

Five Boundaries, One Address Space

A complete implementation guide for a hybrid log: a 48-bit address decoded by threshold, five pointers that slice the address space into semantic regions, a slot-implicit circular buffer, and a step-by-step build of every operation from upsert to fold-over.

Reading time · ~40 min · Sole reference · v1 retired
TL;DR — the design in one screen
  • One 48-bit address space (256 TB). Decoded by threshold — not by fixed-width fields. Change the page size, the segment size, or the memory size without changing the address math.
  • Five pointers — begin_, head_, flushed_until_, read_only_, tail_ — each with a precise meaning about durability, residency, and mutability.
  • Slot = page & mask. No current_page_index field. The slot is the source of truth via modular arithmetic. A flushed page is naturally still in the read cache until head_ moves past it.
  • RecordHeader is 16 bytes packed with bitfields: 48-bit address, 8-bit op, 8-bit flags, 32-bit CRC32C, 32-bit total length. #pragma pack(1) pins the layout.
  • Mutable fraction (default 0.9) controls batching — 10% of RAM sits read-only, ready to flush.
  • Read path is one boundary check + one slot read. Write path is one capacity check + one slot write. No tier-awareness in the hot path.

1 · The address space & threshold decoding

A logical address is a 48-bit value, decoded through a hierarchy of bit-shifts. The same address is interpreted differently by different masks — the hierarchy is what gives the design its flexibility.

Figure 1 · The 48-bit address decoded by threshold. Change page_bits and the segment math still works without modification.

Why "threshold" and not "field width"? Because each decode contains the previous one. The segment mask (2^segment_bits − 1) already includes the page bits; you don't need to know page_bits to compute a segment offset, only to interpret it.

// These are equivalent and just as cheap:
offset_in_page   = addr & (2^page_bits    - 1);
page_in_segment  = (addr & (2^segment_bits - 1)) >> page_bits;
segment_id       = addr >> segment_bits;
The address space is 48 bits, not 64. That gives 2^48 = 256 TB of total addressable log size. The high 16 bits of the 64-bit LogAddress are reserved (you can use them for control flags in-process). If you ever need more than 256 TB, you widen the address bitfield in RecordHeader.

2 · The geometry settings

Three bit-widths, one fraction, one path. Everything else is derived.

page_bits
22 (default) — 4 MB pages
memory_bits
26 (default) — 64 MB resident → 16 pages in RAM
segment_bits
30 (default) — 1 GB segment files on disk
mutable_frac
0.9 (default) — last 10% of RAM is read-only, ready to flush
ro_page_cache
128 (default) — read-side page cache for on-disk pages
dir
filesystem path to the segment files

The invariant that holds the design together: page_bits < segment_bits < 63. memory_bits must be >= page_bits + 1 (at least one page fits in RAM) and ideally < segment_bits in practice (memory should be smaller than a segment).

All the other numbers come from the settings as constexpr methods:

constexpr std::uint64_t PageSize()        const { return 1ULL << page_bits; }
constexpr std::uint64_t MemorySize()      const { return 1ULL << memory_bits; }
constexpr std::uint64_t SegmentSize()     const { return 1ULL << segment_bits; }
constexpr std::uint64_t NumPagesPerSegment() const { return 1ULL << (segment_bits - page_bits); }
constexpr std::uint64_t ResidentPages()   const { return 1ULL << (memory_bits - page_bits); }
Why settings at all? Because the right numbers depend on the workload. A cache wants huge pages and tiny segments; a write-heavy log wants the opposite. Making the geometry runtime-configurable means you can experiment without recompiling, and the math is still constexpr where the settings are known.

3 · The five boundaries

The address space is a single 256 TB line; five pointers slice it into regions with precise meanings. Every read, write, and flush is a question about where an address sits relative to these pointers.

Figure 2 · The five pointers, and the five questions the read/write path can answer in one comparison each.

Each region answers a different question:

regionrangewhat it means
① truncated[0, begin_)Old data past the truncation point. Disk space is free.
② on disk, no RAM[begin_, head_)Durable, but evicted from the read cache. A read goes to disk.
③ in RAM, durable, cached[head_, flushed_until_)Flushed to disk AND still in RAM. The natural read cache.
④ in RAM, not yet flushed[flushed_until_, read_only_)Durable only in memory. Will be flushed in the next batch.
⑤ in RAM, mutable[read_only_, tail_)Active write region. Cannot be flushed until it falls below the read-only line.
Three pointers in a row, but they answer three different questions. flushed_until_ is about durability, read_only_ is about batching, and head_ is about memory pressure. Conflating them means you can't answer "is this data durable?" without also answering "is it in RAM?" — which makes the flush loop harder to write correctly.

4 · The AddressManager class

The class is dumb math. It doesn't allocate memory, doesn't move data, doesn't even know about records. It just tracks five numbers and answers questions about them.

class AddressManager {
    FastLogSettings s_;
    LogAddress begin_         = 0;
    LogAddress head_          = 0;
    LogAddress flushed_until_ = 0;
    LogAddress read_only_     = 0;
    LogAddress tail_          = 0;

  public:
    // Address arithmetic (constexpr, branchless)
    constexpr std::uint64_t PageNumberOf(LogAddress) const;
    constexpr std::uint64_t OffsetInPageOf(LogAddress) const;
    constexpr std::uint64_t SlotOf(LogAddress) const;
    constexpr std::uint64_t SegmentNumberOf(LogAddress) const;
    constexpr std::uint64_t OffsetInSegmentOf(LogAddress) const;
    constexpr std::uint64_t PageNumberInSegmentOf(LogAddress) const;

    // Capacity questions
    constexpr std::uint64_t MemoryCapacity() const;
    constexpr std::uint64_t ResidentSize()   const;
    constexpr std::uint64_t UnflushedBytes() const;
    bool HasCapacityFor(size_t bytes) const;

    // Mutators (caller is responsible for invariants)
    void AdvanceTail(size_t bytes);
    void AdvanceHead(LogAddress new_head);
    void AdvanceReadOnly(LogAddress new_ro);
    void AdvanceFlushed(LogAddress new_flushed);
    void AdvanceBegin(LogAddress new_begin);
};

The mutators have no validation — they just set the number. The caller (your FastLog top-level) is responsible for the invariants:

  • AdvanceTail(bytes) must only be called when HasCapacityFor(bytes) returned true.
  • AdvanceHead(new_head) must only advance past addresses that are no longer referenced by the hash index.
  • AdvanceReadOnly(new_ro) must only advance to an address <= tail_ and >= flushed_until_.
  • AdvanceFlushed(new_flushed) must only advance after a successful disk write, and only past complete pages.
  • AdvanceBegin(new_begin) must only advance past addresses that have been truncated from all segment files.
Why dumb math, not a smart class? Because the address math is hot — it's on every read, every write, every flush. Making the queries constexpr means the compiler inlines them to a couple of bit-shifts. Putting policy (validation, ordering, capacity checks) in the caller keeps the manager as a pure value type you can reason about in one screen.

5 · Monotonicity

The single most important property of the boundary system: every pointer is monotonic non-decreasing. They step forward within a window, jump forward across fold-over, but never decrease. This property is what makes the rest of the engine correct — without it, reads can return stale data, recovery replay becomes ambiguous, and the flush/evict loops can race.

Two kinds of "forward"

Step. The normal case. Every advance moves a pointer by a page (or by a record's slot size for tail_). The writer, flusher, evictor, and truncator all do this.

Jump. Fold-over resets the window — all four of head_, flushed_until_, read_only_, and tail_ jump forward together to a fresh address range past the old tail_. The jump is large (tens of MB by default) but it's still forward.

Figure 3 · Fold-over: the jump forward. Every pointer monotonically increases, but the size of the step can be huge.

Which pointer can do what

pointerwithin a windowacross fold-overacross truncation
begin_doesn’t movedoesn’t movesteps forward (only here)
head_steps forwardjumps forwardsteps forward
flushed_until_steps forwardjumps forward (to new head_)steps forward
read_only_steps forwardjumps forwarddoesn’t move
tail_steps forwardjumps forwarddoesn’t move

begin_ is the special one: it only moves on truncation (one segment file at a time), and it never jumps. The other four can both step and jump.

Why monotonicity matters

Three consequences fall out for free:

  1. Reads are valid forever. If you stored a record at address A while the pointers were at values P₁, ..., P₅, you can still read it as long as begin_ ≤ A < tail_. Because the pointers only move forward, "still valid" is monotone: once valid, always valid (until begin_ passes A on truncation).
  2. The hash index never holds a stale address. Every fold-over updates the index before abandoning the old region. Because the order of operations is enforced and pointers only move forward, you never have to ask "did the index get updated before the window moved?"
  3. Recovery replay is deterministic. Because all pointers are monotonic, the replay order is the same as the write order. You can reconstruct any state by replaying from the last checkpoint forward — no ambiguity, no missing writes.

Invariants that fall out of monotonicity

invariantwhy it holds
begin_ ≤ head_the evictor can only move head_ forward, and truncation moves begin_ forward only past flushed data
flushed_until_ ≤ read_only_the writer checks new_ro ≥ flushed_until_ before pushing RO forward
read_only_ ≤ tail_the writer’s new RO is computed from the current tail_, and tail_ only moves forward
flushed_until_ advances after fsyncorder of operations in the flusher loop is enforced
head_ only advances past pages with no index refsthe evictor scans the index before each step

The most common trap

The writer’s maybe_advance_read_only check is the single line of code that protects the most important invariant:

if (new_ro > am_.GetReadOnly() && new_ro >= am_.GetFlushedUntil()) {
    am_.AdvanceReadOnly(new_ro);
}

Without new_ro >= flushed_until_, the writer could push read_only_ below the durability line, leaving the flusher trying to flush pages that haven’t been written yet. With it, monotonicity holds end-to-end.

If you ever feel tempted to move a pointer backward, stop. "Let me reset tail_ to free up space" — no, fold-over jumps forward to a fresh window. "Let me put head_ back to 0 because the index is empty" — no, eviction advances head_ forward, not backward. Backward motion breaks recovery and breaks reads of older addresses. The right answer is always forward.

6 · The three tiers of storage

One logical address space, three physical homes. The five pointers tell you which home an address currently lives in.

Figure 4 · One address space, three physical homes. The hash index doesn't know or care which tier a record lives in.

Three things follow from this layout:

  1. No data movement on update. Updating a key just appends a new record at tail_ and changes the pointer in the hash index. The old record is left behind; it becomes garbage once nothing references it.
  2. The index never relocates data. Buckets hold stable (tag, address) entries. The address is the only thing that moves on update.
  3. Reads land in one of three places. In the mutable region (fastest), in the read cache (also fast), or on disk (slowest). The address math decides which one — no tier-awareness in the read code.
The boundary is the answer to "where?". You don't ask the storage layer "is this in RAM?" — you compute the slot and read. Whether the slot is "hot" or "cache" or "evicted" is implicit in head_ and flushed_until_. The AddressManager's math does the classification for free.

7 · Slot arithmetic

The circular buffer is implicit.

A page at logical address P always lives at slot P mod ResidentPages. No field tracks "which page is this slot currently holding?" because the slot identity is the page.

Figure 5 · The slot is the page. No side field, no lookup, no check.

The whole "is this page in RAM?" question is implied by the address — if the address is in [head_, tail_), the slot modulo ResidentPages is where the data is, period. The check is the boundary comparison, not a slot lookup.

Why this matters. When a page is flushed to disk, the slot still holds the page's data. We didn't move the bytes; we just appended a copy to the segment file. Until head_ moves past the page, the slot is a free read cache. This is why "flushed" and "in read cache" are the same region in the boundary diagram — they're the same thing in this design.

8 · The PageBuffer

The leaf of the storage hierarchy.

A PageBuffer is a fixed-size byte array with read/write at byte offsets. Nothing more.

class PageBuffer {
  public:
    static constexpr std::size_t kPageSize = 4 * 1024 * 1024;  // 4 MB
    explicit PageBuffer() : bytes_(kPageSize) {}

    // Read a chunk of bytes at a byte offset.
    std::span<const std::byte> Read(std::size_t offset,
                                     std::size_t length) const {
        assert(offset + length <= kPageSize);
        return std::span<const std::byte>(bytes_).subspan(offset, length);
    }

    // Write a chunk of bytes at a byte offset.
    void Write(std::size_t offset, std::span<const std::byte> data) {
        assert(offset + data.size() <= kPageSize);
        std::memcpy(bytes_.data() + offset, data.data(), data.size());
    }

    // Read the entire page (for segment-file I/O).
    std::span<const std::byte> raw() const noexcept { return bytes_; }
    std::span<std::byte>       raw()       noexcept { return bytes_; }

  private:
    std::vector<std::byte> bytes_;  // size = kPageSize, aligned
};

The in-memory log is a std::vector<PageBuffer> of size ResidentPages (or std::array if the size is known at compile time). Indexed by slot, derived from the address.

class InMemoryLog {
  public:
    explicit InMemoryLog(const FastLogSettings& s)
        : settings_(s), pages_(s.ResidentPages()) {}

    // Where to read this address from. RAM = this in-memory log.
    // Returns the slot, or -1 if the address is below head_ (on disk).
    std::optional<SlotIndex> SlotFor(LogAddress addr) const noexcept {
        const auto page = settings_.PageNumberOf(addr);
        if (page < head_page_ || page >= tail_page_) return std::nullopt;
        return static_cast<SlotIndex>(settings_.SlotOf(addr));
    }

    // Write a record at tail_. Returns the address assigned.
    LogAddress Append(Record&& rec) {
        const LogAddress addr = current_tail();
        const auto slot = settings_.SlotOf(addr);
        const auto off  = settings_.OffsetInPageOf(addr);
        pages_[slot].Write(off, rec.AsBytes());
        return addr;
    }

  private:
    FastLogSettings settings_;
    std::vector<PageBuffer> pages_;
    LogAddress head_page_ = 0;   // page-aligned
    LogAddress tail_page_ = 0;   // page-aligned
};
Allocation strategy. Allocate ResidentPages pages up front in the constructor. MemorySize() is the total bytes the log can hold; the pages together must equal that. For 64 MB resident with 4 MB pages, you allocate 16 pages — exactly MemorySize() / PageSize() of them.

9 · The RecordHeader (16 bytes)

The on-disk and in-memory record header is bit-packed into 16 bytes. Same bytes in both places — no marshalling, no translation.

Figure 6 · 16 bytes, every bit assigned. The address lives in 48 bits; the remaining 80 bits carry op, flags, CRC, and length.

The full record is the 16-byte header plus a variable-length payload:

#pragma pack(push, 1)
struct RecordHeader {
    std::uint64_t address : 48;  // logical address (= offset_in_segment for the record)
    std::uint64_t op      : 8;   // RecordOp
    std::uint64_t flags   : 8;   // reserved
    std::uint32_t crc32c;        // over the payload
    std::uint32_t total_length;  // payload bytes
};
#pragma pack(pop)
static_assert(sizeof(RecordHeader) == 16, "");

// Payload layout:
// [ varint key_len ][ key bytes ][ value bytes ]
// varint uses 1 byte for len < 128, 2 bytes otherwise.
// value_len = total_length - varint_size(key_len) - key_len

struct Record {
    RecordHeader header;
    std::vector<std::byte> payload;

    std::size_t TotalSize() const { return sizeof(RecordHeader) + header.total_length; }

    // Serialize for write. The address MUST be set first.
    std::vector<std::byte> AsBytes() const {
        std::vector<std::byte> out(TotalSize());
        std::memcpy(out.data(), &header, sizeof(RecordHeader));
        std::memcpy(out.data() + sizeof(RecordHeader), payload.data(), payload.size());
        return out;
    }
};
Bitfield portability. The order in which the compiler lays out address : 48; op : 8; flags : 8; is implementation-defined. With #pragma pack(1) on x86/ARM64 little-endian, the bytes are [a0..a5 op|flags crc0..crc3 len0..len3]. On a big-endian target the byte order would be different — but the on-disk representation must match the on-memory representation. Use memcpy for serialize/deserialize and the bitfield choice is just a code-clarity issue, not a correctness one.

10 · The hash index

The hash index is the gateway to every read.

It maps key_hash → LogAddress. The value is the address of the latest version of that key — the only thing that moves on update.

Figure 7 · Bucket array with 16-bit tags. The tag lets the common case (no collision) succeed in one cache-line load.
struct HashEntry {
    std::uint16_t tag;        // top 16 bits of the hash — fast reject
    LogAddress   address;     // 64-bit address in the log
};

class Bucket {
  public:
    std::optional<HashEntry> find(std::uint64_t hash) const {
        const std::uint16_t tag = tag_of(hash);
        if (primary_used_ && primary_.tag == tag) return primary_;
        for (const auto& e : overflow_) if (e.tag == tag) return e;
        return std::nullopt;
    }
    void upsert(std::uint64_t hash, LogAddress addr) {
        const std::uint16_t tag = tag_of(hash);
        if (primary_used_ && primary_.tag == tag) { primary_.address = addr; return; }
        for (auto& e : overflow_) if (e.tag == tag) { e.address = addr; return; }
        if (!primary_used_) { primary_ = {tag, addr}; primary_used_ = true; return; }
        overflow_.push_back({tag, addr});
    }
    template <typename F> void for_each(F&& f) const {
        if (primary_used_) f(primary_);
        for (const auto& e : overflow_) f(e);
    }
  private:
    static constexpr std::uint16_t tag_of(std::uint64_t h) { return static_cast<std::uint16_t>(h >> 48); }
    HashEntry               primary_{};
    bool                    primary_used_ = false;
    std::vector<HashEntry> overflow_;
};

class HashIndex {
  public:
    explicit HashIndex(std::size_t buckets = 1u << 20) : buckets_(buckets) {}
    // FNV-1a. Replace with xxh3 in production.
    static std::uint64_t hash(std::span<const std::byte> key);
    std::optional<LogAddress> lookup(std::uint64_t h) const;
    void upsert(std::uint64_t h, LogAddress addr);
    template <typename F> void for_each_live(F&& f) const {
        for (const auto& b : buckets_) b.for_each(f);
    }
  private:
    std::vector<Bucket> buckets_;
};
Tag bits are the secret weapon. A 16-bit tag (top bits of the hash) lets you reject non-matching entries in one cache-line load before doing the full compare. With a healthy load factor (~0.5), most buckets have one entry; the tag check is the entire lookup.

11 · The mutable fraction

The mutable_frac (default 0.9) splits the in-memory region into two bands: the last 10% is read-only, the first 90% is the active write target.

Figure 8 · The 90/10 split. The writer fills the mutable region, the flusher drains the RO region.

The flow looks like this:

1

Writer fills mutable region

Each upsert appends at tail_, advances it. tail_ creeps toward read_only_.

2

Writer pushes the read-only line forward

When tail_ approaches read_only_, call AdvanceReadOnly(tail_ − mutable_window). Old pages fall entirely below the new line and become immutable.

3

Flusher drains the RO region

A background loop (or your event loop) writes [flushed_until_, read_only_) to disk. On success, call AdvanceFlushed(read_only_).

4

Eviction catches up

Once a page is in the on-disk log and no hash index entry references it, the head can advance. New pages are now eligible to overwrite the freed slots.

The 10% is not magic. It controls the tradeoff between flush latency and write amplification. Smaller (5%): more frequent flushes, less data per flush. Larger (20%): fewer flushes, more data lost if you crash before the next flush. Pick what your durability SLA needs.

12 · The upsert path

An upsert is append-only.

It always writes to tail_ and updates the hash index — no reading of the old value is required.

Figure 9 · Upsert is append-only. The old record (if any) is simply abandoned in the log.
LogAddress FastLog::upsert(std::string_view key, std::span<const std::byte> value) {
    // 1. Build the payload and compute its size.
    std::vector<std::byte> payload = make_payload(key, value);
    const std::size_t slot_size = sizeof(RecordHeader) + payload.size();

    // 2. Capacity check. If false, evict first.
    if (!am_.HasCapacityFor(slot_size)) {
        flush_until_capacity(slot_size);
    }

    // 3. Stamp the address BEFORE writing (so the record knows its own addr).
    const LogAddress addr = am_.GetTail();
    Record rec;
    rec.header.address    = addr;
    rec.header.op         = RecordOp::Upsert;
    rec.header.flags      = 0;
    rec.header.total_length = static_cast<std::uint32_t>(payload.size());
    rec.header.crc32c     = crc32c(payload.data(), payload.size());
    rec.payload           = std::move(payload);

    // 4. Write to the page at SlotOf(addr), OffsetInPageOf(addr).
    const auto slot = am_.SlotOf(addr);
    const auto off  = am_.OffsetInPageOf(addr);
    auto bytes = rec.AsBytes();
    mem_.pages_[slot].Write(off, bytes);

    // 5. Advance tail.
    am_.AdvanceTail(slot_size);

    // 6. Maybe push the read-only line forward.
    maybe_advance_read_only();

    // 7. Update the hash index to point at the new record.
    const auto h = HashIndex::hash(as_bytes(key));
    index_.upsert(h, addr);

    return addr;
}
The address is stamped before the write. The record's own address is the first field in the header. By computing addr = tail_ and writing it into the header before the page write, the record is self-describing. A read can verify "yes, this is the record I was looking for" by comparing the header address with the one from the index.

13 · The read path

The read path is the simplest of the three operations. The hash lookup is constant time; the only variable cost is whether the record is in RAM or on disk.

1

Hash lookup

Compute h = hash(K), compute b = h % N, walk the bucket's chain. The 16-bit tag rejects mismatches in one cache-line load. Result: a LogAddress.

2

Boundary checks

addr < begin_ → truncated, not found. addr >= tail_ → never written, not found. Otherwise it's a valid address.

3

Read the page

addr >= head_ → in RAM, read at slot. addr < head_ → on disk, read from segment file (with the page cache in front). Either way, you get a 16-byte header + payload.

4

Validate the record

Compare header.address with the address you read it from. Compute CRC32C over the payload and compare with header.crc32c. Compare key bytes with the requested key.

5

Interpret and return

Upsert → return value bytes. Delete → not found. Copy → chase the bridge (up to 4 hops).

std::optional<std::vector<std::byte>> FastLog::read(std::string_view key) {
    const auto h = HashIndex::hash(as_bytes(key));
    auto addr = index_.lookup(h);
    if (!addr) return std::nullopt;

    // Bounded chase for Copy records.
    for (int hop = 0; hop < 4; ++hop) {
        if (*addr < am_.GetBegin() || *addr >= am_.GetTail()) return std::nullopt;

        // Read the page (RAM or disk).
        std::vector<std::byte> page;
        if (*addr >= am_.GetHead()) {
            const auto slot = am_.SlotOf(*addr);
            const auto off  = am_.OffsetInPageOf(*addr);
            page = read_page_from_ram(slot, off);
        } else {
            const auto seg  = am_.SegmentNumberOf(*addr);
            const auto off  = am_.OffsetInSegmentOf(*addr);
            page = disk_.ReadPage(seg, off, ro_cache_);
        }

        // Parse the header.
        RecordHeader hdr;
        std::memcpy(&hdr, page.data(), sizeof(RecordHeader));
        if (hdr.address != *addr) return std::nullopt;  // slot got recycled

        // Validate CRC.
        const std::span<const std::byte> body(page.data() + sizeof(RecordHeader),
                                                hdr.total_length);
        if (crc32c(body.data(), body.size()) != hdr.crc32c) return std::nullopt;

        // Validate the key (catches hash collisions).
        if (!key_matches(body, key)) return std::nullopt;

        // Interpret.
        if (hdr.op == RecordOp::Upsert) return extract_value(body, key);
        if (hdr.op == RecordOp::Delete) return std::nullopt;
        if (hdr.op == RecordOp::Copy) {
            LogAddress target;
            std::memcpy(&target, body.data() + copy_target_offset(body, key), sizeof(LogAddress));
            addr = target;
            continue;
        }
        return std::nullopt;
    }
    return std::nullopt;
}
Validation is the safety net. The address check catches slot-recycling bugs. The CRC32C catches disk corruption. The key match catches hash collisions. All three run on every read; all three are cheap. Skipping any of them means a single bug can silently return wrong data.

14 · The delete path (tombstones)

A delete is an append of a record with op = Delete and an empty value. The hash index points to the new record; the old record becomes garbage.

LogAddress FastLog::remove(std::string_view key) {
    std::vector<std::byte> payload = make_payload(key, {});  // value is empty
    const std::size_t slot_size = sizeof(RecordHeader) + payload.size();
    if (!am_.HasCapacityFor(slot_size)) flush_until_capacity(slot_size);

    const LogAddress addr = am_.GetTail();
    Record rec;
    rec.header.address    = addr;
    rec.header.op         = RecordOp::Delete;
    rec.header.flags      = 0;
    rec.header.total_length = static_cast<std::uint32_t>(payload.size());
    rec.header.crc32c     = crc32c(payload.data(), payload.size());
    rec.payload           = std::move(payload);

    const auto slot = am_.SlotOf(addr);
    const auto off  = am_.OffsetInPageOf(addr);
    mem_.pages_[slot].Write(off, rec.AsBytes());
    am_.AdvanceTail(slot_size);
    maybe_advance_read_only();

    const auto h = HashIndex::hash(as_bytes(key));
    index_.upsert(h, addr);
    return addr;
}

Why tombstones instead of physical deletes?

  • Append-only writes stay simple — same code path as upsert, different op code.
  • Recovery is deterministic — replaying the log gives the same final state, because tombstones are just records.
  • Physical deletes are the job of fold-over — when memory pressure forces compaction, the dead records get reaped.
Watch the tombstone lifetime. A tombstone must survive long enough to override any older in-memory version of the same key. In this design the tombstone is at tail_ (newest) and the old version is below it. Fold-over should not lose a tombstone that points to the latest state — keep this in mind when you write the fold-over logic.

15 · The flush flow

Flushing is the act of moving pages from the mutable region to the on-disk segment files. It's the path that closes the durability gap.

1

Determine the flush range

Read-only pages are [flushed_until_, read_only_). Snap this to page boundaries — you can only flush complete pages, otherwise partial pages would have to be re-read at recovery time.

2

Write pages to disk

For each page in the range: determine the segment number and offset-in-segment from the address, write the page's bytes. Use a write-ahead log or per-segment append to keep disk I/O sequential.

3

fsync the affected segment files

Durability requires that the bytes are on stable storage, not in the OS page cache. Call fdatasync (or fsync) on each affected segment file before advancing the boundary.

4

Advance flushed_until_

On success, am_.AdvanceFlushed(read_only_). Now everything in [head_, flushed_until_) is durable AND in RAM (it's the read cache).

5

Try to advance head_

For each page in the now-flushed range: is the hash index still pointing at any address in this page? If not, the page is evictable. Advance head_ past it.

void FastLog::flush() {
    const LogAddress ro_page_aligned = page_align_down(am_.GetReadOnly());
    if (ro_page_aligned <= am_.GetFlushedUntil()) return;  // nothing to flush

    // Write all pages in [flushed_until_, ro_page_aligned) to disk.
    for (LogAddress a = am_.GetFlushedUntil(); a < ro_page_aligned; a += settings_.PageSize()) {
        const auto slot = am_.SlotOf(a);
        const auto page_bytes = mem_.pages_[slot].raw();
        const auto seg  = am_.SegmentNumberOf(a);
        const auto off  = am_.OffsetInSegmentOf(a);
        disk_.WritePage(seg, off, page_bytes);
    }
    disk_.Sync();  // fsync all dirty segments

    am_.AdvanceFlushed(ro_page_aligned);
    try_advance_head();
}
Order matters. Write, fsync, advance. If you advance the boundary before fsync, a crash can leave the index saying "durable" when the bytes are still in the page cache. If you fsync but don't advance, you're just being slow without being wrong. Always do the slow thing in the right order.

16 · The fold-over flow

Fold-over is the operation that prevents the in-memory log from filling up with garbage. It compacts the live records into a fresh window, leaving the dead records to be overwritten by future writes.

Figure 10 · Fold-over compacts the in-memory log by keeping only the latest live version of each key.
void FastLog::fold_over() {
    // 1. Snapshot every entry's live address.
    struct LiveRef { std::uint64_t hash; LogAddress addr; std::size_t key_len; };
    std::vector<LiveRef> live;
    index_.for_each_live([&](const HashEntry& e) {
        // Read the key length from the record (need it for the new record).
        const std::size_t key_len = read_key_length(e.address);
        live.push_back({e.hash, e.address, key_len});
    });

    // 2. Compute the new window. Place it ahead of the current tail so
    //    we don't have to move live data twice.
    const LogAddress new_window = round_up_to_page(am_.GetTail());

    // 3. Copy each live record into the new window. Write a Copy record
    //    at the new address, with the value body pointing to the old one.
    am_.AdvanceHead(new_window);   // abandon the old in-memory region
    am_.AdvanceReadOnly(new_window);
    am_.AdvanceTail(new_window);

    for (auto& ref : live) {
        const std::size_t slot_size = sizeof(RecordHeader) + ref.key_len + sizeof(LogAddress);
        if (!am_.HasCapacityFor(slot_size)) {
            // The new window is too small. Either re-fold or grow.
            throw std::runtime_error("fold-over: new window too small");
        }
        const LogAddress new_addr = am_.GetTail();
        Record rec;
        rec.header.address    = new_addr;
        rec.header.op         = RecordOp::Copy;
        rec.header.total_length = static_cast<std::uint32_t>(ref.key_len + sizeof(LogAddress));
        rec.header.crc32c     = 0;  // TODO: compute over the payload
        rec.payload.resize(rec.header.total_length);
        write_varint(rec.payload.data(), ref.key_len);
        write_key_bytes(rec.payload.data() + varint_size(ref.key_len), ref.addr);
        std::memcpy(rec.payload.data() + varint_size(ref.key_len) + ref.key_len,
                    &ref.addr, sizeof(LogAddress));

        const auto slot = am_.SlotOf(new_addr);
        const auto off  = am_.OffsetInPageOf(new_addr);
        mem_.pages_[slot].Write(off, rec.AsBytes());
        am_.AdvanceTail(slot_size);

        // Update the hash index to point at the new address.
        index_.upsert(ref.hash, new_addr);
    }
}
The Copy record bridges old and new. The body of a Copy record contains the key bytes (for verification) followed by the original address. On read, you verify the key, follow the bridge, and read from the old address — which is in the abandoned region. As long as the old region hasn't been overwritten yet, the read still works. Fold-over is the only operation that changes an address without an explicit write; the read path handles it via the Copy chase.

17 · Crash recovery

Recovery is what makes the log durable across crashes. The shape: persist the AddressManager state, persist the hash index periodically, replay the unflushed tail on startup.

1

Persist the AddressManager state

On every AdvanceFlushed, write the current begin_, head_, flushed_until_, read_only_, and the settings to a metadata file. tail_ is recoverable from the index + segment files (it's the highest address with any record).

2

Persist the hash index

Periodically (or on shutdown), dump the hash index to a file. One file per bucket array, or a flat file with all entries. The index is small compared to the data — a 1M-bucket index with 500K entries is ~16 MB.

3

Replay on startup

Read the metadata file. Read the hash index. Open the segment files. For any record at address addr with flushed_until_ <= addr < tail_ (i.e. the unflushed tail), re-apply it: read the record, update the hash index. Now tail_ matches the new in-memory tail.

void FastLog::recover() {
    // 1. Load metadata.
    MetadataFile meta = read_metadata(settings_.dir);
    settings_ = meta.settings;
    am_ = AddressManager(settings_, meta.begin_);

    // 2. Load hash index.
    index_ = read_hash_index(settings_.dir / "index.bin");

    // 3. Open segment files lazily (mmap or fopen on first access).

    // 4. Replay the unflushed tail from the last flushed checkpoint.
    for (const auto& entry : index_.all_entries()) {
        if (entry.address >= am_.GetFlushedUntil() && entry.address < am_.GetTail()) {
            // The record is in the unflushed tail. Re-apply it.
            // (For a sketch, this just means trusting the index's tail.)
        }
    }

    // 5. Resume normal operation. The next write goes to the current tail_.
}
Sketch-scope recovery. For a learning build, the simplest recovery is: persist metadata + index on clean shutdown, lose unflushed data on crash. Real production needs a write-ahead log (WAL) or group-commit to survive crashes without losing the unflushed tail. That's a whole additional system; out of scope for the first cut.

// ─── Settings (your FastLogSettings) ──────────────────────
struct FastLogSettings {
    std::uint32_t page_bits    = 22;
    std::uint32_t memory_bits  = 26;
    std::uint32_t segment_bits = 30;
    double        mutable_frac = 0.9;
    std::uint32_t ro_page_cache = 128;

    void Validate() const;
    constexpr std::uint64_t PageSize()    const { return 1ULL << page_bits; }
    constexpr std::uint64_t MemorySize()  const { return 1ULL << memory_bits; }
    constexpr std::uint64_t SegmentSize() const { return 1ULL << segment_bits; }
    constexpr std::uint64_t PageMask()    const { return PageSize() - 1; }
    constexpr std::uint64_t SegmentMask() const { return SegmentSize() - 1; }
    constexpr std::uint64_t ResidentPages() const { return 1ULL << (memory_bits - page_bits); }
    constexpr std::uint64_t SlotMask()    const { return ResidentPages() - 1; }
    constexpr std::uint64_t NumPagesPerSegment() const { return 1ULL << (segment_bits - page_bits); }
};

// ─── Address + AddressManager (your code) ─────────────────
using LogAddress = std::uint64_t;

class AddressManager {
  public:
    AddressManager(const FastLogSettings& s, LogAddress first)
        : s_(s), tail_(first), head_page_(first / s.PageSize()) {}

    constexpr std::uint64_t PageNumberOf(LogAddress a) const { return a >> s_.page_bits; }
    constexpr std::uint64_t OffsetInPageOf(LogAddress a) const { return a & s_.PageMask(); }
    constexpr std::uint64_t SlotOf(LogAddress a) const { return PageNumberOf(a) & s_.SlotMask(); }
    constexpr std::uint64_t SegmentNumberOf(LogAddress a) const { return a >> s_.segment_bits; }
    constexpr std::uint64_t OffsetInSegmentOf(LogAddress a) const { return a & s_.SegmentMask(); }
    constexpr std::uint64_t PageNumberInSegmentOf(LogAddress a) const { return OffsetInSegmentOf(a) >> s_.page_bits; }
    constexpr LogAddress    PageStart(std::uint64_t page) const { return page << s_.page_bits; }

    constexpr LogAddress GetBegin()         const { return begin_; }
    constexpr LogAddress GetHead()          const { return head_aligned(); }
    constexpr LogAddress GetFlushedUntil()  const { return flushed_until_; }
    constexpr LogAddress GetReadOnly()      const { return read_only_; }
    constexpr LogAddress GetTail()          const { return tail_; }

    constexpr std::uint64_t MemoryCapacity() const { return s_.MemorySize(); }
    constexpr std::uint64_t ResidentSize()   const { return tail_ - GetHead(); }
    constexpr std::uint64_t UnflushedBytes() const { return tail_ - flushed_until_; }
    bool HasCapacityFor(std::size_t bytes) const {
        return ResidentSize() + bytes <= MemoryCapacity();
    }

    void AdvanceTail(std::size_t bytes) { tail_ += bytes; }
    void AdvanceHead(LogAddress new_head) { head_page_ = new_head / s_.PageSize(); }
    void AdvanceReadOnly(LogAddress new_ro) { read_only_ = new_ro; }
    void AdvanceFlushed(LogAddress new_flushed) { flushed_until_ = new_flushed; }
    void AdvanceBegin(LogAddress new_begin) { begin_ = new_begin; }

  private:
    constexpr LogAddress head_aligned() const { return head_page_ * s_.PageSize(); }
    FastLogSettings s_;
    LogAddress begin_         = 0;
    std::uint64_t head_page_  = 0;
    LogAddress flushed_until_ = 0;
    LogAddress read_only_     = 0;
    LogAddress tail_          = 0;
};

// ─── InMemoryLog (the slot-indexed ring) ──────────────────
class InMemoryLog {
  public:
    explicit InMemoryLog(const FastLogSettings& s) : s_(s), pages_(s.ResidentPages(), PageBuffer(s.PageSize())) {}

        const auto page = s_.PageNumberOf(a);

19 · Build order

12 incremental steps.

Each one is independently testable. Don't move to the next until the current one passes its test.

  1. FastLogSettings + AddressManager. Implement the settings validation, the constexpr address math, and the boundary mutators. Test: round-trip every address through PageNumberOf / OffsetInPageOf / SlotOf / SegmentNumberOf. The test from the original post is a good starting point.
  2. RecordHeader serialization. Implement Record::AsBytes and Record::FromBytes using memcpy. Test: write a record, read it back, every field matches. Use static_assert on sizeof(RecordHeader) == 16.
  3. PageBuffer. Implement the read/write at byte offsets. Test: write N bytes at offset M, read them back. Run with ASan to catch buffer overruns.
  4. InMemoryLog with the slot ring. Allocate ResidentPages pages in the constructor. Implement SlotFor to return the slot or nullopt based on the in-memory window. Test: a series of writes at known addresses, verify the slot math.
  5. HashIndex. Bucket array + 16-bit tags + overflow chains. Test: insert N keys, look them all up, force collisions with crafted keys.
  6. FastLog::upsert + read + remove. Wire it all together. Implement the three operations using the path from §11–§13. Test: write, read back, overwrite, delete, hash-collision key, read-returns-nullopt-for-deleted.
  7. OnDiskLog (single segment file). Append a full page; read a page by segment + offset. Test: write 100 pages, read them all back, verify bytes match.
  8. FastLog::flush. Drain [flushed_until_, read_only_) to disk, advance flushed_until_. Test: upsert, flush, read, verify the data is still correct (it was in the read cache anyway, but verify).
  9. Eviction via head advance. After flush, find pages that no index entry references, advance head_ past them. Test: fill the log, force eviction, verify reads still work (they go to disk now).
  10. Multi-segment on-disk log. When a segment fills, open a new one. Test: write enough data to span multiple segments, read across the boundary.
  11. FastLog::fold_over. The Copy-record dance. Test: write a key 10 times, fold over, read the latest value, verify the Copy chain resolves.
  12. Recovery. Persist metadata + index on shutdown, load on startup. Test: upsert, flush, close, reopen, verify the state is preserved.
Don't try to write it all at once. Steps 1–5 are the foundation. Step 6 is the first time you have a working KV store — celebrate that. Steps 7–10 add durability. Steps 11–12 add the clever bits. Each step has a test that proves the previous step's invariant still holds.

Five pointers. One address. Threshold decoding. The rest is bookkeeping.

That's the whole design — enough to start a build, enough to make every design decision you need before you write the first line of production code.
