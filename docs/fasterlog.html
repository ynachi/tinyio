Storage engine internals

The FASTER Hybrid Log, taken apart

A profound walkthrough of Microsoft's FASTER hybrid log — built specifically so you can ship a clean single-threaded port without losing the soul of the design.

Reading time · ~25 min · Audience · someone about to build this
TL;DR — the mental model in one screen
  • There is one logical log, with a 64-bit address per record, split into an in-memory tail and an on-disk head.
  • A concurrent hash index maps key_hash → address. The address is the only thing that moves on update.
  • The in-memory log is split into a small mutable region (lock-free writes) and a read-only region (frozen, flushable).
  • When memory fills up, you do an in-place flush (read-only pages → disk) or a fold-over (compact live records in place).
  • Recovery = persisted hash index + replay from a recent on-disk checkpoint.
  • Single-threaded removes epoch protection, CAS, and concurrent overflow chains — but the rest of the data model stays identical.

1 · The three tiers of storage

FASTER's central trick is that there is no "cache + index + storage" — there is one log with three physical homes. The hash index doesn't know which tier a record lives in; it just knows a 64-bit address. Decoding that address tells you exactly where to read.

Figure 1 · The hybrid log is a single address space spanning RAM and disk. The hash index doesn't care which tier a record lives in.

Three things follow from this layout:

  1. No data movement on update. Updating K1 just appends a new record and changes the pointer in the hash index. The old record is left behind — it becomes garbage once nothing can read it.
  2. The index never relocates data. Buckets hold stable (hash, address) entries. This is what makes the cache hot and the operations cheap.
  3. Reads can land in three places. The hash lookup returns an address; the read routine decodes it to know whether to read RAM, SSD, or both.

2 · The 64-bit address space

An address isn't a pointer — it's a packed descriptor. FASTER splits the 64 bits into three fields. A common layout:

Figure 2 · One possible 64-bit address split. The exact field widths are tunable; what matters is that the address is self-describing.

The "segment" field is the key. It tells you which physical log the record lives in (mutable in-memory, read-only in-memory, on-disk segment 0, on-disk segment 1, etc). With one bit-mask and one shift you know exactly where to read:

fn location(addr: u64) -> Location {
    let segment = (addr >> 56) & 0xFF;
    let page    = (addr >> 32) & 0x00FF_FFFF;
    let offset  = addr & 0xFFFF_FFFF;
    match segment {
        0 => Location::Mutable(page, offset),
        1 => Location::ReadOnly(page, offset),
        _ => Location::Disk(segment - 2, page, offset),
    }
}

For your single-threaded port, you can simplify: 1 bit for in-memory vs on-disk, then a byte offset within that log. The complexity is optional. The principle — address, not pointer — is not.

Why an address, not a pointer? Pointers die with the process and change with every relocation. Addresses survive crashes, encode "where to look" without being a memory address, and let the same hash entry point to RAM or SSD without type games. The address also doubles as the record's version — every record carries its own LSN in the header, which is what makes recovery and fold-over deterministic.

3 · The in-memory log layout

The in-memory log is a sequence of fixed-size pages — typically 32 KB, but any power of two works. Each page has a status and holds a packed stream of records.

Figure 3 · The in-memory log is a sequence of pages, each with a status that determines how it can be touched.

Three invariants the log maintains:

  1. Writes only ever go to the tail (last mutable page).
  2. A mutable page becomes read-only when full (or when you explicitly flush it).
  3. A read-only page can be flushed to disk and its memory reused.

For a single-threaded build, the page status is just an enum and the tail pointer is a single counter. No atomics, no compare-and-swap. The structure is identical to the multi-threaded version — only the synchronization changes.

The "mutable" status isn't about concurrency. In FASTER it's about deferred batching: writes go into a mutable page that's cheap to append to, then frozen once full, so flushes can happen in big aligned chunks. You'll want this even single-threaded — it makes flushes cheap and lets the on-disk log align nicely to 4 KB / 32 KB boundaries.

4 · The hash index

The hash index is the gateway to every read. It maps key_hash → 64-bit address. FASTER uses a fixed-size bucket array with overflow chaining — the simplest concurrent-friendly hash structure.

Figure 4 · Each bucket has a primary slot and an overflow chain. The full hash is stored, not just the bucket index, so collisions can be disambiguated.

Two important things to notice:

  • Only the full hash lives in the entry — not the key. The key is read from the log when you actually want to verify a read. This keeps the index small and cache-hot.
  • On an upsert, you walk the chain looking for a matching hash, and either update the existing entry in place or append a new one. The key never needs to be touched in the index.
struct HashEntry {
    hash:    u64,   // full 64-bit hash
    address: u64,   // 64-bit address in the hybrid log
    tag:     u16,   // 16-bit tag (top bits of hash) for fast rejection
}

struct Bucket {
    primary:  Option<HashEntry>,  // first slot — always present
    overflow: Vec<HashEntry>,     // chained collisions
}
Tag bits are the secret weapon. A 16-bit tag (top bits of the hash) lets you reject non-matching entries in one cache-line load before doing the full compare. It's why FASTER's hash index is fast even at 50M+ entries.

5 · Record format

Every record in the log has the same on-disk/on-memory layout. A record is a header followed by a key and a value.

Header (16 B)
version (8 B)  ·  key_len (2 B)  ·  value_len (4 B)  ·  op (1 B)  ·  checksum (1 B)
op ∈ {Upsert(0), Delete(1), Copy(2)}  ·  version = record's own address
Key
key_len bytes · raw key bytes  ·  used to verify hash collisions
Value
value_len bytes · raw value bytes  ·  absent for delete records

Three tricks to be aware of:

  • The version field equals the record's address. That makes recovery a re-playable log: each record knows where it lives, so you can reconstruct an index from a snapshot + tail with zero ambiguity.
  • Variable-length records are aligned to 8 bytes by padding the slot. This makes offset arithmetic within a page a single division rather than a scan.
  • The "Copy" operation appears after a fold-over or a deep copy from disk to the read cache. It lets the same record appear at two addresses without duplicating storage — only the value bytes (the body) are repeated, the header still points at the original record.

6 · The upsert path

An upsert is the simplest of the three operations. It always appends to the log and updates the hash index — no reading of the old value is required.

Figure 5 · Upsert is append-only. The old record (if any) is simply abandoned in the log.
fn upsert(&mut self, key: &[u8], value: &[u8]) {
    let h = hash(key);
    let slot_size = align8(RECORD_HEADER + key.len() + value.len());

    // 1. Reserve a slot in the mutable region
    if self.tail + slot_size > self.mem_log.end() {
        self.freeze_mutable();      // see §9
    }
    let addr = self.tail;
    self.tail += slot_size;

    // 2. Write the record (its own address = its version)
    let rec = Record::upsert(addr, key, value);
    rec.write_at(self.mem_log, addr);

    // 3. Update the hash index
    let bucket = self.index.bucket_mut(h);
    if let Some(entry) = bucket.find_mut(h) {
        entry.address = addr;            // overwrite in place
    } else {
        bucket.push_overflow(h, addr);   // add a new chain link
    }
}

Note: the index walk is bounded by the chain length. In a healthy hash index with 2× more buckets than keys, chains are 1–2 entries long. In the worst case (load factor > 1) you walk longer — for that, FASTER has a "genuine overflow" path that lives in a separate structure. For your port, just grow the table or use Robin-Hood hashing if you want better behavior under pressure.

7 · The read path

A read is where the design really pays off. The hash lookup is constant time; the only variable cost is whether the record is in RAM or on disk.

1

Hash and bucket lookup

Compute h = hash(key), compute b = h % N, read the bucket. The primary slot is one cache line. The 16-bit tag rejects mismatches before any other work.

2

Walk the chain, get the address

For each chain entry with a matching tag, compare the full 64-bit hash. On a hit, you have a 64-bit address. The chain length is the variable cost — usually 1.

3

Decode the address to a location

Look at the segment bits: mutable RAM, read-only RAM, or on-disk segment N. Each maps to a different read routine.

4

Read the record

For RAM: pointer arithmetic into the page buffer, read the header, return the value slice. For disk: page in the on-disk page, decompress if needed, then read the record. For disk records, optionally copy into the read cache on the way back.

5

Verify, interpret, return

Read the key bytes from the record and confirm they match the requested key (catches false-positive hash collisions). Then interpret the op: Upsert returns the value, Delete returns None / "not found", Copy follows its pointer to the real data.

fn read(&mut self, key: &[u8]) -> Option<&[u8]> {
    let h = hash(key);
    let bucket = self.index.bucket(h);

    // Walk the chain
    let addr = bucket.find(h)?.address;
    let loc = self.decode(addr);

    // Read the record from the right tier
    let rec = match loc {
        Location::Mutable(p, o)   => self.mem_log.page(p).record_at(o),
        Location::ReadOnly(p, o)  => self.mem_log.page(p).record_at(o),
        Location::Disk(s, p, o)   => self.disk.read(s, p, o)?,
    };

    // Verify the key matches (hash collisions)
    if rec.key() != key {
        return self.find_next_chain_entry(h, key);
    }

    match rec.op() {
        Op::Upsert => Some(rec.value()),
        Op::Delete => None,
        Op::Copy   => self.read_at(rec.copy_target()),
    }
}
The read cache is optional but very effective. If disk reads dominate, a small in-memory ring of recently-read on-disk pages cuts latency by 10–100× for hot keys that have aged out of the main log. For a single-threaded build, a simple LRU of 64–256 pages is enough.

8 · The delete path (tombstones)

FASTER does not delete in place. A delete is an append of a record with op = Delete and an empty value. The hash index points to the new record, the old record becomes garbage.

fn delete(&mut self, key: &[u8]) {
    let h = hash(key);
    let slot_size = align8(RECORD_HEADER + key.len());  // no value

    // Reserve + write a Delete record (same as upsert, but op = Delete)
    let addr = self.append_record(Record::delete(addr, key), slot_size);
    self.index.upsert_entry(h, addr);   // same routine as upsert
}

Why tombstones instead of physical deletes?

  • Append-only writes stay simple and lock-free (in the multi-threaded version).
  • Recovery is deterministic — replaying the log gives the same final state.
  • Physical deletes are the job of fold-over — when memory pressure forces compaction, the dead records get reaped. You can also drop them when their pages are flushed to disk and the index no longer references them.
Watch the tombstone lifetime. A tombstone must survive long enough to override any older in-memory version of the same key. In FASTER this is handled by the fold-over / flush ordering — the tombstone is never "below" the fold-over watermark. In your single-threaded build it's automatic, but document it so future-you doesn't introduce a bug.

9 · Freezing and flushing

When the mutable page fills up (or you decide to flush for durability), three operations happen, in this order:

1

Freeze the mutable page

Mark the current page as ReadOnly. The tail pointer now points at the next page. New writes go there. No reads are affected — the read path treats mutable and read-only pages identically.

2

Open a new mutable page

If the in-memory log is full, reuse a freed page (or allocate a new one). The old page can now be flushed without blocking future writes.

3

Flush the read-only page to disk

Append the page to the on-disk log. The on-disk log is also a sequence of fixed-size segments; the new page becomes the tail of the current segment. Once the segment is full, a new segment is started. After a successful flush, the in-memory page can be recycled.

Figure 6 · In-place flush: a read-only page is appended to the on-disk log and its in-memory slot is recycled.

Two things to track carefully:

  • Head vs tail. The in-memory log can become circular. The head advances when the oldest page is fully flushed and no index entry references it. The tail advances on every write. The two pointers are what tell you "is this address in memory or on disk".
  • Page pinning. A page can't be reused while any hash entry might still reference it. In single-threaded mode, you can scan the index at recycle time (cheap if your index is small, expensive if it's huge — for the port, scan is fine). In multi-threaded FASTER this is the epoch protocol.

10 · Fold-over compaction

Fold-over is what makes the log genuinely "hybrid" — it's the operation that prevents the on-disk log from growing forever and the in-memory log from filling up with garbage.

When memory pressure is high and the on-disk log is also saturated, FASTER compacts the in-memory log in place: it walks the in-memory pages, finds the latest version of every key still referenced by the hash index, and writes those records to the start of the in-memory log. Everything else is dropped.

Figure 7 · Fold-over compacts the in-memory log by keeping only the latest live version of each key.
fn fold_over(&mut self) {
    // 1. Snapshot every entry's live address
    let live: Vec<(u64, u64)> = self.index.iter()
        .map(|e| (e.hash, e.address))
        .collect();

    // 2. Compact the in-memory log: walk live addresses, copy
    //    each record to the head of the log, get its new address.
    self.mem_log.reset_head();
    for (_, old_addr) in &live {
        let rec = self.mem_log.read_at(*old_addr);
        let new_addr = self.mem_log.append(&rec);
        self.pending_index_updates.push((hash, new_addr));
    }

    // 3. Apply the new addresses back to the index
    for (h, new_addr) in self.pending_index_updates.drain(..) {
        self.index.upsert_address(h, new_addr);
    }

    // 4. Pages beyond the new tail are now garbage
    self.mem_log.reclaim();
}
Fold-over is the cost of being append-only. It's also why this design scales: fold-over work is proportional to the number of live records, not the number of writes. A workload with 10× write-amplification and a 90% overwrite ratio gets most of that space amplification back for free.

11 · Crash recovery

Recovery is the part most people skip and then regret. FASTER's recovery is clean: checkpoint the hash index, replay the tail of the log.

Figure 8 · Recovery is a snapshot + tail replay. Bounded by the size of the tail, not the size of the database.
For your single-threaded port: persist the hash index as a flat file (just dump every HashEntry in order) and append every record to a file as it's written. On startup: mmap the index file, then sequentially scan the on-disk log from the snapshot's tail offset and replay into the mutable region. No fancy crash recovery, no torn-write protection — for a learning build, just make sure you sync to disk on a clean shutdown.

12 · What single-threaded lets you drop

Building single-threaded is a design simplification, not a design change. The data model is identical. The pieces you can remove:

Multi-threaded FASTER Single-threaded equivalent
Epoch-based memory reclamation Drop it. Single owner of memory means no readers can outlive a write.
CAS-based hash chain update Plain &mut access. Update in place.
Concurrent overflow chains A Vec<HashEntry> per bucket. Append freely.
Atomic tail pointer A single u64. No atomics.
Thread coordination around freezing Just freeze it when full. No readers to coordinate with.
Lock-free record reservation Compute slot, write, move on. No CAS loop.
Read cache LRU with locks Plain LRU. HashMap + VecDeque.

What you keep (because they're part of the model, not the synchronization):

  • The mutable / read-only distinction. Even single-threaded, batching flushes is worth it.
  • Append-only writes with the index pointing at the latest address.
  • Fold-over compaction. Same code, no atomics.
  • The on-disk log + checkpoint + replay recovery model.
  • The 64-bit address space (or your simplified version of it).

13 · Skeleton code

A concrete starting point in Rust-flavored pseudocode. Treat this as the shape of the code, not the final form.

// ─── Constants ─────────────────────────────────────────────
const PAGE_SIZE:    usize = 32 * 1024;
const SLOT_ALIGN:   usize = 8;
const BUCKET_COUNT: usize = 1 << 20;     // 1M buckets

// ─── Address ───────────────────────────────────────────────
#[derive(Copy, Clone)]
struct Address(u64);

impl Address {
    fn segment(&self) -> u8  { (self.0 >> 56) as u8 }
    fn page(&self)    -> u32 { ((self.0 >> 32) & 0x00FF_FFFF) as u32 }
    fn offset(&self)  -> u32 { (self.0 & 0xFFFF_FFFF) as u32 }
    fn encode(seg: u8, page: u32, off: u32) -> Self {
        Address(((seg as u64) << 56) | ((page as u64) << 32) | off as u64)
    }
}

#[derive(Debug)]
enum Location {
    Mutable(u32, u32),    // page, offset
    ReadOnly(u32, u32),
    Disk(u8, u32, u32),   // segment, page, offset
}

// ─── Record ────────────────────────────────────────────────
#[derive(Copy, Clone)]
enum Op { Upsert, Delete, Copy }

struct Record {
    version:  u64,    // = the record's own Address
    key_len:  u16,
    val_len:  u32,
    op:       Op,
    checksum: u8,
    // followed by `key_len` bytes of key and `val_len` bytes of value
}

// ─── Hash index ────────────────────────────────────────────
struct HashEntry {
    tag:     u16,        // top 16 bits of hash — fast reject
    address: Address,
}

struct Bucket {
    primary:  Option<HashEntry>,
    overflow: Vec<HashEntry>,
}

impl Bucket {
    fn find(&self, hash: u64) -> Option<&HashEntry> {
        let tag = (hash >> 48) as u16;
        if let Some(e) = &self.primary {
            if e.tag == tag { return Some(e); }
        }
        self.overflow.iter().find(|e| e.tag == tag)
    }
    fn upsert(&mut self, hash: u64, addr: Address) {
        let tag = (hash >> 48) as u16;
        if let Some(e) = self.primary.iter_mut().find(|e| e.tag == tag) {
            e.address = addr; return;
        }
        if let Some(e) = self.overflow.iter_mut().find(|e| e.tag == tag) {
            e.address = addr; return;
        }
        match &mut self.primary {
            None => { self.primary = Some(HashEntry { tag, address: addr }); }
            Some(_) => self.overflow.push(HashEntry { tag, address: addr }),
        }
    }
}

struct HashIndex {
    buckets: Vec<Bucket>,
}

impl HashIndex {
    fn bucket(&self, hash: u64) -> &Bucket {
        &self.buckets[hash as usize % self.buckets.len()]
    }
    fn bucket_mut(&mut self, hash: u64) -> &mut Bucket {
        let n = self.buckets.len();
        &mut self.buckets[hash as usize % n]
    }
}

// ─── Pages ─────────────────────────────────────────────────
#[derive(Clone, Copy, PartialEq)]
enum PageStatus { Free, Mutable, ReadOnly }

struct Page {
    bytes:  Vec<u8>,
    status: PageStatus,
}

// ─── In-memory log ─────────────────────────────────────────
struct MemLog {
    pages:     Vec<Page>,
    head_idx:  usize,     // index of the page at the head address
    tail_idx:  usize,     // index of the page at the tail address
    tail_off:  u32,       // offset within the tail page
    head_addr: u64,       // address of the first byte of the log
}

impl MemLog {
    fn freeze_current(&mut self) {
        self.pages[self.tail_idx].status = PageStatus::ReadOnly;
        self.tail_idx = (self.tail_idx + 1) % self.pages.len();
        self.tail_off = 0;
    }
    fn append(&mut self, rec: &Record) -> Address {
        let slot = slot_size(rec);
        if self.tail_off + slot as u32 > PAGE_SIZE as u32 {
            self.freeze_current();
        }
        let addr = Address::encode(1, self.tail_idx as u32, self.tail_off);
        rec.write_into(&mut self.pages[self.tail_idx].bytes[self.tail_off..]);
        self.tail_off += slot as u32;
        addr
    }
}

// ─── On-disk log ───────────────────────────────────────────
struct DiskLog { /* file handle + current segment + tail offset */ }

// ─── The store itself ──────────────────────────────────────
struct HybridKV {
    hash:   HashIndex,
    mem:    MemLog,
    disk:   DiskLog,

14 · Build order

Suggested order for the single-threaded build. Each step is independently testable.

  1. Address encoding + record layout. Get the binary format right first. Write a hex-dump test to confirm round-trips.
  2. In-memory log with a single page. Append, read, scan. Verify with a unit test that a round-trip through the log gives back the same bytes.
  3. Hash index. Bucket array + overflow. Test with collisions: insert N keys, look them all up.
  4. Read and upsert end-to-end. At this point you have a working in-memory KV store. Stop and benchmark — make sure the basics are solid.
  5. Multi-page in-memory log + freeze. Add the mutable → read-only transition. Make sure reads still work after freezing.
  6. Append to a log file on disk + read back. Add the on-disk log as a simple append-only file. This is now a "bigger than memory" store.
  7. Address decoding into mutable/read-only/disk. The read path now has to look in three places.
  8. Freeze → flush pipeline. When a page becomes read-only, write it to disk. Recycle the in-memory slot.
  9. Fold-over. When in-memory is full and on-disk is also saturated, compact. Watch the space amplification number go down.
  10. Checkpoint + replay. Persist the hash index, record the tail address, replay from there on startup.
  11. Read cache (optional but recommended). A 64-page LRU on the on-disk read path. Big latency win for hot out-of-memory keys.
  12. Iterator / scan support (optional). Scans walk the on-disk log or in-memory log in address order. This is one of FASTER's distinctive features.
You don't need to implement all of this to learn the design. Steps 1–5 give you the in-memory engine. Steps 6–8 give you durability. Steps 9–11 give you the full picture. Step 12 is a stretch.

That's the whole hybrid log — one address space, one index, two physical homes, and a fold-over to keep it from filling up.
